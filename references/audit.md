# audit.md · 用问题清单决定交付状态

审计回答的是“这份方案能否按现在的信息执行”，不是“旅行一定顺利”。自动脚本发现结构、时间和算术问题；模型/人工检查来源是否真的支持结论。两者都必须留下结果。

## 两阶段检查

规划完成后先做内容审计：每条开放/预约/交通/价格事实是否指向合适来源、适用于旅行日期、且没有把体验线索升格为规则。渲染后再做产物审计：MD 与 HTML 是否来自同一数据、内容指纹/文件大小是否匹配、可见内容是否覆盖、HTML 是否离线且无敏感信息。

## 问题级别

| 级别 | 含义 | 可以怎样交付 |
| --- | --- | --- |
| blocking | 预约失败仍在主行程、时间重叠、闭馆、返程冲突、预算下界超限、悬空引用、凭据泄漏 | 不能交付为可执行方案，必须修复或请用户取舍 |
| conditional | 信息过期、待预约、路线未知、预算上界风险、日期未覆盖 | 可交付条件版；页面须显示条件、截止时间、行动和替代 |
| info | 需要注意但不改变当前可执行性 | 写入说明或复查队列 |

可执行状态只在没有 blocking 和 conditional 时成立；否则分别为 `draft` 或 `conditional`。用户确认某项选择不等于预约已确认，也不等于事实仍在有效期内。

## 修复循环

每轮只处理能解释的根因：修改地点会失效依赖它的路线、事实和行程项；修改日期会失效时效和天气；恢复历史版本会失效先前核查。把受影响对象加入 recheck queue，重新查证后才允许升级状态。达到无法在合理轮次内消除的问题，应停下并向用户说明取舍，不伪造“已核实”。

## 人工/模型核查问题

- 来源正文是否直接支持“开放、预约、价格、末班、入场规则”等写入的结论？
- 来源是否针对正确地点、分馆、日期、年龄/票种与时段？
- 多来源相矛盾时是否保留冲突，而不是任选一个？
- 社媒笔记是否只作为体验、排队或拍照线索？
- 替代项是否也有地点、时间、交通、开放和费用的可执行性？
- 输出文案是否区分 confirmed、verified、conditional、unknown 与 estimate？

## 最小验收

1. schema、引用、日期/时区、开放窗口、路段留时、预算和锁定安排通过确定性校验。
2. 变更会产生可追踪的依赖失效与复查清单。
3. 历史快照不可被同版本内容覆盖；恢复生成新版本并清除过期核查状态。
4. provider 未接入、拒绝或失败时仍有明确的基础方案与降级提示。
5. 同一 `trip.json` 可生成离线 MD/HTML，交付前通过 manifest 和敏感信息检查。
6. 自动测试、跨平台 CI 与视觉检查分别报告，不以任一项替代另一项。
