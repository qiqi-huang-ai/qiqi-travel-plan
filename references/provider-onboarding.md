# provider-onboarding.md · 新用户接口选择

读取时机：新行程的 S0 初始化，或用户问“需要提供什么 API / 能不能接接口”时。它是正式规划前的必经门，不完成选择就不进入研究和行程编排。

## 1. 先给选择，不先索要密钥

用一段简短说明让用户选择：

> 这次旅行规划可以直接用普通联网资料完成，也可以接入可选接口来提高某些环节的覆盖。接口不是必需品；你可以选择“本次不接入”“接入已有安全配置”“接入但需要配置指导”。我不会让你把 API Key 直接发在聊天里。

选项至少包括：

| 选项 | 适用 | 需要用户提供 | 不接的影响 |
| --- | --- | --- | --- |
| 本次不接入 | 先做基础路线、预算和出发前清单 | 无 | 社媒体验、实时地图路线或超出天气覆盖范围的内容可能只能估算或待查 |
| 接入已有安全配置 | 用户已经在宿主配置了接口 | 只确认接口名称和本次是否授权使用 | 具体限制取决于该接口；仍需先 dry-run |
| 接入但需要配置指导 | 用户希望接入但尚未配置 | 接口名称；按指导在安全配置中完成 | 配置完成前不能调用，先走降级路径 |

不允许把“有工具”当成“用户已授权”。用户没有明确选择时，状态是“待选择”，必须停在入口询问，不得默认接入，也不得默认跳过。

选择后运行 `python3 scripts/provider_gate.py <trip.json> --choice connect|configure --budget <本次上限> --out <candidate.json>`，或在不接入时运行 `--choice decline`，用候选文件记录 `decisions[]` 和 `capabilities[]`；不得覆盖私有源文件。接入选项不允许省略预算。

## 2. 用能力解释接口，而不是列一堆 API 名

按实际需求逐项询问，最多推荐一次：

| 接口 / 能力 | 能补什么 | 不是它能保证的 | 配置边界 |
| --- | --- | --- | --- |
| TikHub（小红书 App V2） | 排队、亲子体验、餐饮和近期变化线索；可采样笔记与评论 | 不能证明开放、票价、余票、天气或路线；图片也不自动获得转载许可 | 用户明确同意请求次数上限后，放入宿主安全配置或本地 `TIKHUB_API_KEY`；不在聊天中发送令牌 |
| 高德 / 地图工具 | 地理编码、地点消歧、路线时间范围 | 不等于已买票或实时拥堵保证 | 仅使用已授权且预算明确的地图能力；未配置时用公开路线或保守估算 |
| 天气提供方 | 目标日期在覆盖范围内的预报 | 不能伪造超出覆盖范围的远期天气 | 默认可用 Open-Meteo；超出覆盖范围改为季节参考 + 出发前复核 |

## 3. TikHub 选择话术

需求方向清楚后只推荐一次：

> 可选增强：接入 TikHub 后，我可以补充小红书里的排队、亲子体验、餐饮和近期变化线索。它不是必需的，可能产生第三方费用；我仍会把影响行程的事实交叉核查。你可以选：①使用已有安全配置；②需要配置指导；③这次先不用。请同时给一个请求次数上限（标准默认 40 次，深度默认 100 次，可自定义更低）。

### 选择的利弊

- 接入的好处：能补充近期体验摩擦，例如排队、带儿童是否方便、餐饮等；这些能帮助调整节奏和备选方案。
- 接入的代价：可能产生第三方费用；结果受样本、作者和时间影响，不能证明开放、票价、余票、路线或天气；还会增加隐私与过期复查成本。
- 不接入的好处：零配置、零 TikHub 请求成本、资料边界更简单；基础行程仍可完成。
- 不接入的代价：排队、踩坑、亲子体验和近期变化只能标为未知或依赖普通公开资料。

选择“使用已有安全配置”时，只检查是否实际可用；选择“需要配置指导”时才展示注册、邮箱验证、后台查看费用、生成令牌、放入安全配置的步骤；选择“不用”时停止推荐和调用。

## 4. 交付中必须说明的差异

- 已接入并成功调用：说明实际请求次数、资料覆盖范围、费用估算状态和“社媒只是体验证据”的限制。
- 用户拒绝或未配置：在 `decisions[]` 记录拒绝/未配置，在 `capabilities[]` 写 `tikhub: unavailable / denied`，并在 MD/H5 的资料说明中写明：基础规划仍可完成，但社媒体验覆盖较少，排队、踩坑和近期变化可能保留为未知。
- 接口失败：不把失败响应当资料；保留失败原因与降级路径，继续基础规划。
