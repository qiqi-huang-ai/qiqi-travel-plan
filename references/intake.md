# intake.md · 将旅行愿望变成可核查的计划输入

这一步的产物不是行程，而是一份可修改的需求档案。已知信息直接登记；未知项写 `unknown`，不要为了进入下一步而猜值。

## 先选数据能力

新用户先得到三种清晰选项：

| 选择 | 可得到什么 | 需要提供什么 | 不能得到什么 |
| --- | --- | --- | --- |
| 不接接口 | 基于用户资料、公开可读材料与明确标注的估算完成离线方案 | 无 | 实时路线、可用天气窗口、社媒体验样本会缺失或更早过期 |
| 接地图/天气 | 地理编码、路线候选与临近出发日天气可写入证据 | 用户自行配置的地图 key；天气无需 key 时也须允许调用 | 不能替代场馆官网、票务系统或用户确认 |
| 接 TikHub | 可将小红书公开笔记作为“体验线索”收集 | 用户主动配置 `TIKHUB_API_KEY`，并确认请求上限 | 笔记不是营业规则，不能单独把预约、开放或价格标成 verified |

只在用户选中且明确允许网络请求时读取凭据。dry-run 用来展示预计请求，绝不读取 key 或消耗额度。能力不可用时，`capabilities` 必须写 availability、原因、fallback 和对交付的影响。

## 收集顺序

按以下顺序提问，已有答案不重复问；每轮只问会改变路线、预算或预订决策的缺口。

1. 出发地、目的地或候选目的地、往返日期、过夜数、同行人数与年龄段。
2. 已买交通、已订住宿、已预约活动及其时间、车站/机场、可读凭证；这些都是不可擅自改动的锁定项。
3. 预算模式（总额或人均）、币种、人数口径、已付金额和可超支边界。儿童、老人是否计入预算必须明说。
4. 交通偏好、每日最早/最晚出门、午休、无障碍、饮食、行李、体力与旅行节奏。
5. 必去、可选、明确排除项，以及为什么；“都可以”应登记为低权重偏好，不应被伪装成必去。
6. 输出形式、语言、是否公开分享；公开版默认去掉联系人、订单、精确住址和用户材料。

## 目的地尚未确定

候选比较必须同口径：每个候选都展示抵达成本/时长、旅行日期是否有硬冲突、适合同行人群的理由、必须预约的不确定性、以及不能确认的信息。先请用户选目的地，再深入规划；除非用户明确要求，否则不为多个目的地同时做完整日程。

## 用户材料和外部信息

用户上传的订单、截图、链接、朋友推荐都先记录“可读性”和来源类型。看不清或没有目标日期的材料只能作为线索。外部信息以 `SourceRecord`、`FactRecord` 分开存：来源证明“看到什么”，事实说明“据此暂时采用什么安排”。

## 何时重新确认

调研后必须回问的情况包括：必去项与锁定交通冲突、预算只能在删减后成立、儿童/老人需要改变节奏、预约尚未开放、或找到的规则与用户材料相反。把可选方案、代价和推荐理由一并呈现，等待选择后再写入 `decisions`。

## 不应追问的事

不索取 API key、完整身份证、支付密码、乘车二维码或不必要的精确住址；不把“推荐餐厅”变成餐饮偏好审问；不在用户已明确的选择上反复确认。敏感信息仅在本地私有资料中最小化保存，不能进入公开 HTML。
